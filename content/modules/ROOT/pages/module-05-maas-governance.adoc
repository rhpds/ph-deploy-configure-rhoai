= Module 5: Governing Access with Models-as-a-Service (MaaS)
:navtitle: Module 5: MaaS Governance
:toc: macro
:toclevels: 1
:icons: font

Serving a model is not enough for shared environments — access must be governed. {maas} adds a
subscription and rate-limit layer over model serving, backed by an API gateway
({rhcl} / Kuadrant) and a PostgreSQL-backed API-key store.

[IMPORTANT]
====
*Technology Preview.* Serving vLLM models through {maas} is a Technology Preview feature in
{rhoai} {rhoai_version}. APIs and behaviour may change; it is not supported for production use.
====

== Learning objectives

By the end of this module you will be able to:

* Enable {maas} in the `DataScienceCluster` and dashboard
* Provision the MaaS PostgreSQL database and `maas-db-config` secret
* Install {rhcl}, register Kuadrant, and bootstrap the gateway
* Install the gateway-native serving operators (Leader Worker Set, JobSet) and deploy a model as an
  `LLMInferenceService` attached to the MaaS gateway
* Publish and govern it with `MaaSModelRef`, `MaaSSubscription`, and `MaaSAuthPolicy` custom resources
* Mint an API key, call the model through the gateway, and demonstrate token rate limiting (HTTP 429)
* Enable User Workload Monitoring so served-model metrics reach the dashboard, then view vLLM engine
  metrics and MaaS per-subscription token telemetry

== Prerequisites

* xref:module-04-vllm-serving.adoc[Module 4] complete (KServe single-model serving working)
* Cluster-admin to enable {maas} in the `DataScienceCluster`; {rhcl} and cert-manager installable

== Exercise 1: Provision PostgreSQL and secrets

The MaaS API needs its database *before* it is enabled, or `maas-api` will crash-loop.

. Create the database credentials and connection secret:
+
[source,bash,role="execute"]
----
POSTGRES_PASSWORD=$(openssl rand -base64 16 | tr -d '=+/')
# The Red Hat rhel9/postgresql-15 image reads POSTGRESQL_* env vars (not POSTGRES_*)
# to create the user, password, and database on first start.
oc create secret generic postgres-creds -n redhat-ods-applications \
  --from-literal=POSTGRESQL_USER=maas \
  --from-literal=POSTGRESQL_PASSWORD="${POSTGRES_PASSWORD}" \
  --from-literal=POSTGRESQL_DATABASE=maas
oc create secret generic maas-db-config -n redhat-ods-applications \
  --from-literal=DB_CONNECTION_URL="postgresql://maas:${POSTGRES_PASSWORD}@postgres:5432/maas?sslmode=disable"
----

. Deploy PostgreSQL:
+
[source,bash,role="execute"]
----
oc apply -k manifests/05-maas/postgres -n redhat-ods-applications
oc rollout status deploy/postgres -n redhat-ods-applications
----

=== Verify

* The `postgres` deployment is `Available` and both secrets exist in `redhat-ods-applications`.

With the database running, let's install the API gateway layer that MaaS uses to enforce subscriptions.

== Exercise 2: Install Red Hat Connectivity Link and bootstrap the gateway

The order matters here. The Kuadrant custom resource and the gateway both depend on
resources that do not exist until the operators have finished installing, so each step
below waits for its prerequisite before moving on.

. Install the {rhcl} and cert-manager operators (subscriptions only). The RHCL subscription
  includes a timeout tuning for Authorino's ext_authz service:
+
Inspect the manifest:
+
[source,bash,role="execute"]
----
cat manifests/05-maas/connectivity-link/connectivity-link-subscription.yaml
----
+
[source,yaml]
----
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: rhcl-operator
  namespace: openshift-operators
spec:
  channel: stable
  name: rhcl-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  config:
    env:
      - name: AUTH_SERVICE_TIMEOUT    # <1>
        value: "10s"
----
<1> Increases the Authorino ext_authz timeout from the default (200ms) to 10s. Under load
    the default timeout is too tight — Authorino can't validate the API key in time, and the
    gateway returns an intermittent HTTP 500 instead of retrying.
+
[source,bash,role="execute"]
----
oc apply -k manifests/05-maas/connectivity-link
----

. Wait for both operator CSVs to reach `Succeeded` — the Kuadrant CRD is not registered
until the {rhcl} operator install completes:
+
[source,bash,role="execute"]
----
oc wait --for=jsonpath='{.status.state}'=AtLatestKnown \
  subscription/rhcl-operator -n openshift-operators --timeout=5m
oc wait --for=jsonpath='{.status.phase}'=Succeeded \
  csv/$(oc get subscription rhcl-operator -n openshift-operators -o jsonpath='{.status.currentCSV}') \
  -n openshift-operators --timeout=5m
oc wait --for=jsonpath='{.status.state}'=AtLatestKnown \
  subscription/openshift-cert-manager-operator -n cert-manager-operator --timeout=5m
oc wait --for=jsonpath='{.status.phase}'=Succeeded \
  csv/$(oc get subscription openshift-cert-manager-operator -n cert-manager-operator -o jsonpath='{.status.currentCSV}') \
  -n cert-manager-operator --timeout=5m
----
+
image::10-rhcl-operator.png[RHCL Operator,link=self,window=blank,width=800]

. Register Kuadrant now that its CRD exists. The `Kuadrant` CR bootstraps Authorino
  (authentication) and Limitador (rate limiting) in the `kuadrant-system` namespace:
+
Inspect the manifest:
+
[source,bash,role="execute"]
----
cat manifests/05-maas/connectivity-link/kuadrant.yaml
----
+
[source,yaml]
----
apiVersion: kuadrant.io/v1beta1
kind: Kuadrant
metadata:
  name: kuadrant
  namespace: kuadrant-system
spec:
  observability:
    enable: true   # <1>
----
<1> Creates ServiceMonitors/PodMonitors that scrape Limitador and Authorino metrics into
    the data-science MonitoringStack. Without this, the *Usage* tab in the Observability
    dashboard has no token consumption data.
+
[source,bash,role="execute"]
----
oc apply -f manifests/05-maas/connectivity-link/kuadrant.yaml
oc wait --for=condition=Ready kuadrant/kuadrant -n kuadrant-system --timeout=5m
----

. Let Authorino trust the cluster service CA — without this, Authorino cannot verify the
  `maas-api` TLS certificate and every API key request returns a gateway 500 error.
+
WARNING: This step adds trusted CA material only. Do *not* enable Authorino's `listener` or `oidcServer` TLS and do *not* set `mtls.authorino: true` on the Kuadrant CR — the `kuadrant-system` namespace has no Istio sidecars, so the Kuadrant `ext_authz` filter speaks plaintext gRPC on `:50051`. Enabling either form of TLS makes the gateway unable to reach Authorino and turns every request into a `500`.
+
[source,bash,role="execute"]
----
oc apply -f manifests/05-maas/connectivity-link/authorino-service-ca-trust.yaml
# Give the service-ca / network operators a moment to populate the ConfigMaps, then mount them.
oc wait --for=jsonpath='{.data.service-ca\.crt}' configmap/authorino-service-ca \
  -n kuadrant-system --timeout=2m
oc patch authorino authorino -n kuadrant-system --type=merge -p '{"spec":{"volumes":{"items":[{"name":"ca-trust","mountPath":"/etc/pki/tls/certs","configMaps":["authorino-trusted-ca-bundle","authorino-service-ca"]}]}}}'
oc rollout status deploy/authorino -n kuadrant-system --timeout=5m
----

. Create the MaaS gateway. The manifests carry a `$\{CLUSTER_DOMAIN}` placeholder, so they are
built with `oc kustomize` and rendered through `envsubst` before applying — the gateway name,
namespace, and `GatewayClass` are fixed values the MaaS controller expects and must not be changed.
+
There are two modes; pick the one that matches your cluster:
+
--
*ClusterIP + Route (default — RHDP, bare-metal, on-prem, disconnected).* These clusters have no
LoadBalancer provider, so the gateway `Service` is created as `ClusterIP` and exposed by an OpenShift
`Route` that re-encrypts to it (the same pattern the built-in `data-science-gateway` uses):

[IMPORTANT]
====
Using a `ClusterIP` service type with the Gateway API is not currently a supported configuration.
A support exception is required — see
link:https://redhat.atlassian.net/browse/RFE-9734[RFE-9734] for status and to track when this
becomes fully supported.
====

[source,bash,role="execute"]
----
export CLUSTER_DOMAIN=$(oc get ingress.config cluster -o jsonpath='{.spec.domain}')
oc kustomize manifests/05-maas/gateway/clusterip | envsubst '${CLUSTER_DOMAIN}' | oc apply -f -
# On clusters without a LoadBalancer provider, the gateway Service is type LoadBalancer
# but stays <pending> externally. Manually set the service status with the Route hostname
# so the gateway reports the external URL and the maas-api can discover it.
SVC=$(oc get svc -n openshift-ingress -l gateway.networking.k8s.io/gateway-name=maas-default-gateway \
  -o jsonpath='{.items[0].metadata.name}')
oc patch svc "${SVC}" -n openshift-ingress --subresource=status --type=merge \
  -p "{\"status\":{\"loadBalancer\":{\"ingress\":[{\"hostname\":\"maas.${CLUSTER_DOMAIN}\"}]}}}"
oc wait --for=condition=Programmed gateway/maas-default-gateway \
  -n openshift-ingress --timeout=5m
# The maas-ui pod caches the gateway URL at startup. Restart it so it
# re-discovers the gateway through the new Route.
oc rollout restart deploy/maas-ui -n redhat-ods-applications
oc rollout status deploy/maas-ui -n redhat-ods-applications --timeout=60s
----
+
. The `maas-ui` pod reaches the MaaS API via the gateway's external hostname. On this cluster
  the pod network cannot route to the external ingress VIP — patch the deployment with a
  `hostAliases` entry so the pod resolves the gateway hostname directly to the gateway service:
+
[source,bash,role="execute"]
----
GW_IP=$(oc get svc -n openshift-ingress \
  -l gateway.networking.k8s.io/gateway-name=maas-default-gateway \
  -o jsonpath='{.items[0].spec.clusterIP}')
GW_HOST=$(oc get svc -n openshift-ingress \
  -l gateway.networking.k8s.io/gateway-name=maas-default-gateway \
  -o jsonpath='{.items[0].status.loadBalancer.ingress[0].hostname}')

oc patch deploy maas-ui -n redhat-ods-applications --type=json \
  -p "[{\"op\":\"add\",\"path\":\"/spec/template/spec/hostAliases\",\"value\":[{\"ip\":\"${GW_IP}\",\"hostnames\":[\"${GW_HOST}\"]}]}]"

oc rollout status deploy/maas-ui -n redhat-ods-applications --timeout=60s
----
+
NOTE: This step is specific to this lab environment where the pod network cannot route to the
cluster's external ingress VIP. In production the `maas-ui` pod would resolve the gateway
hostname normally.

*LoadBalancer (cloud — AWS/ROSA/OSD, or on-prem with MetalLB).* Only use this if your cluster has a
LoadBalancer provider; otherwise the gateway `Service` stays `<pending>` and the gateway never reaches
`Programmed=True`:

[source,bash,role="execute"]
----
export CLUSTER_DOMAIN=$(oc get ingress.config cluster -o jsonpath='{.spec.domain}')
oc kustomize manifests/05-maas/gateway/loadbalancer | envsubst '${CLUSTER_DOMAIN}' | oc apply -f -
oc wait --for=condition=Programmed gateway/maas-default-gateway \
  -n openshift-ingress --timeout=5m
----
--

=== Verify

* Both operator CSVs report `Succeeded`, `kuadrant/kuadrant` is `Ready`, and
  `gateway/maas-default-gateway` in `openshift-ingress` reports `Programmed=True`.
* In ClusterIP mode, the gateway route is `Admitted` and the `maas-gw-service-tls` secret has been
  provisioned by the service-ca operator:
+
[source,bash,role="execute"]
----
oc get route maas-gateway-route -n openshift-ingress
----


TIP: The `maas-default-gateway` is now your single entry point for all governed model traffic. Every model published through MaaS shares this gateway, which enforces API-key authentication, subscription rate limits, and telemetry at the network layer — before a request reaches vLLM.

== Exercise 6: Mint an API key and call the model

MaaS API Keys can be created from the {rhoai-short} dashboard or from the CLI. We are going to use the CLI for this exercise,
however, you can create an API key from the dashboard by clicking on the "API Keys" tab and select a subscription from the dropdown:

image::26-maas-api-key-create.png[MaaS API Key Create,link=self,window=blank,width=800]

and then clicking the "Create API Key" button.

image::27-maas-api-key.png[MaaS API Key,link=self,window=blank,width=800]

When using the CLI, MaaS issues API keys through the `maas-api` endpoint, not as a Kubernetes Secret. Authenticate with
your OpenShift token to mint a key bound to the subscription, then call the model through the
gateway.

. Resolve the gateway host and mint an API key (returned only once):
+
[source,bash,role="execute"]
----
export CLUSTER_DOMAIN=$(oc get ingresses.config.openshift.io cluster -o jsonpath='{.spec.domain}')
export HOST="https://maas.${CLUSTER_DOMAIN}"
export API_KEY=$(curl -sSk -X POST "${HOST}/maas-api/v1/api-keys" \
  -H "Authorization: Bearer $(oc whoami -t)" \
  -H "Content-Type: application/json" \
  -d '{"name":"workshop-key","expiresIn":"1h","subscription":"qwen25-05b-demo"}' | jq -r .key)
echo "API key: ${API_KEY:0:12}..."
----

. Discover the published model id from the catalog. The gateway supports two routing modes —
  *body-based* (recommended) and *path-based*:
+
[source,bash,role="execute"]
----
# The gateway and maas-api may still be warming up the first time you call them, so the very first
# /models request can return a transient non-JSON body (jq then errors with "Invalid numeric
# literal"). Retry until the catalog parses and reports a ready model.
for attempt in $(seq 1 20); do
  MODEL_JSON=$(curl -sSk "${HOST}/maas-api/v1/models" -H "Authorization: Bearer ${API_KEY}")
  echo "$MODEL_JSON" | jq -e '[.data[]? | select(.ready==true)][0]' >/dev/null 2>&1 && break
  echo "models catalog not ready yet (attempt ${attempt}/20); retrying..."; sleep 5
done
if ! echo "$MODEL_JSON" | jq -e '[.data[]? | select(.ready==true)][0]' >/dev/null 2>&1; then
  echo "ERROR: no ready models in catalog after retries. Check:"
  echo "  oc get maasmodelref,maassubscription -A"
  echo "  oc get authpolicy maas-gateway-auth -n openshift-ingress -o jsonpath='{.status.conditions[?(@.type==\"Enforced\")].status}'"
  echo "Raw catalog response: $MODEL_JSON"
fi
# MODEL_ID: the full catalog id (publishers/<ns>/models/<name>) — used for body-based routing.
export MODEL_ID=$(echo "$MODEL_JSON" | jq -re '[.data[] | select(.ready==true)][0].id')
# MODEL_NAME: the short name vLLM serves — last segment of the catalog id.
export MODEL_NAME=$(echo "$MODEL_ID" | sed 's|.*/||')
# MODEL_PATH: the gateway path for path-based routing (/<namespace>/<resource-name>).
export MODEL_PATH=$(echo "$MODEL_JSON" | jq -re '[.data[] | select(.ready==true)][0] | ((.url | gsub("^https?://[^/]+"; "")) | if length > 1 then . else null end) // ("/"+.owned_by)')
echo "Model ID:   $MODEL_ID"
echo "Model name: $MODEL_NAME"
echo "Model path: ${HOST}${MODEL_PATH}"
----
+
--
*Body-based routing (recommended).* Send all requests to `${HOST}/v1/chat/completions` and
specify the model in the JSON body using the full catalog `id` — the same
OpenAI-compatible pattern that SDKs and application frameworks use:

[source,bash,role="execute"]
----
curl -sSk "${HOST}/v1/chat/completions" \
  -H "Authorization: Bearer ${API_KEY}" \
  -H "Content-Type: application/json" \
  -d "{\"model\":\"${MODEL_ID}\",\"messages\":[{\"role\":\"user\",\"content\":\"Hello\"}],\"max_tokens\":50}" | jq .
----

image::16-maas-model-success.png[MaaS Body-Based Routing Model Success,link=self,window=blank,width=800]

[NOTE]
====
*Body-based routing requires the full catalog `id`* (e.g.
`publishers/rhoai-deploy/models/qwen25-05b`), not the short model name (`qwen25-05b`). The
gateway resolves the model from the body and matches it against the catalog — the short name
returns a 404. Path-based routing uses the short name in the *body* and the namespace path
in the *URL*.
====

*Path-based routing.* Encode the model in the URL path. Useful for debugging (each model
has a distinct URL) but couples the client to the cluster's namespace layout:

[source,bash,role="execute"]
----
curl -sSk "${HOST}${MODEL_PATH}/v1/chat/completions" \
  -H "Authorization: Bearer ${API_KEY}" \
  -H "Content-Type: application/json" \
  -d "{\"model\":\"${MODEL_NAME}\",\"messages\":[{\"role\":\"user\",\"content\":\"Hello\"}],\"max_tokens\":50}" | jq .
----
--

[NOTE]
====
*The first call can fail while the gateway warms up.* Immediately after the MaaS stack starts (or a
key is freshly minted), the very first `/maas-api/v1/models` request may return a transient non-JSON
body — `jq` reports `Invalid numeric literal` and `MODEL_ID`/`MODEL_PATH` come back empty. This is
warm-up, not a failure: the retry loop above re-fetches until the catalog parses, and subsequent
calls succeed. Likewise, the first *chat* completion can be slow (cold vLLM engine, ~30s) and may
even time out once — run it again and it returns in ~2s.
====

=== Verify

* The chat request returns *HTTP 200* with a completion. A request with no `Authorization` header
  returns *HTTP 401*.

== Module summary

**What you accomplished:**

* Stood up the full {maas} stack: PostgreSQL, gateway ({rhcl}/Kuadrant), User Workload Monitoring, serving-path operators, and observability backend
* Published `{cpu_model}` as an `LLMInferenceService` governed by a `MaaSSubscription` with a 100-token/minute rate limit
* Minted an API key, called the model through the gateway, triggered rate limiting (HTTP 429), and observed token telemetry per subscription

**Key takeaways:**

* Ordering is critical: the database must be running before MaaS is enabled in the DSC, and the serving-path operators (LWS, JobSet) must be installed before MaaS activation
* `LLMInferenceService` is MaaS's gateway-native object — it registers directly with the gateway; `MaaSModelRef` does not accept a plain `InferenceService`
* Two metric paths feed the dashboard: vLLM engine metrics via User Workload Monitoring → Thanos, and MaaS token telemetry via Limitador → Kuadrant `TelemetryPolicy`
