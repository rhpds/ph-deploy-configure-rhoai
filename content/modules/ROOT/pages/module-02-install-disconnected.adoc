= Module 2: Installing RHOAI (Disconnected / Air-gapped)
:navtitle: Module 2: Install (Disconnected)
:toc: macro
:toclevels: 1
:icons: font

Many production clusters run air-gapped behind a firewall. In this module you install {rhoai}
{rhoai_version} without direct internet access by mirroring operator images to a local registry and
installing from a local `CatalogSource`. A Quay.io proxy pull-through cache is offered as a
lighter-weight alternative.

[NOTE]
====
This module reaches the same "RHOAI Ready" end state as xref:module-01-install-connected.adoc[Module 1].
Run whichever path matches your target environment; you do not need both.
====

[IMPORTANT]
====
*Allow 2-4+ hours.* The mirror-to-disk and disk-to-registry phases download and process ~314 GB of
operator images and tar archives. The workflow is functionally complete — every step runs
end-to-end — but the I/O-bound phases (tar creation, registry push) take significant wall-clock
time. Plan accordingly.
====

[IMPORTANT]
====
*Scope: RHOAI only.* This module mirrors only {rhoai-short} — the `rhods-operator` and its dependent
operator images — onto a cluster where OpenShift is *already installed* disconnected. It does *not*
mirror the OpenShift platform release payload. Mirroring all of OpenShift for a from-scratch
air-gapped install is a larger exercise; refer to the references at the end of this module for the
complete disconnected OpenShift workflow.
====

== Learning objectives

By the end of this module you will be able to:

* Install the oc-mirror v2 CLI and provide it registry credentials from the cluster pull secret
* Pin the imageset configuration to the cluster's OpenShift version
* Mirror the {rhoai-short} operator and dependent images with oc-mirror v2 (to disk, then to a registry)
* Deploy a Quay mirror registry and push the disk archive into it
* Install a local `CatalogSource` with an `ImageDigestMirrorSet` / `ImageTagMirrorSet`
* Complete a `DataScienceCluster` install offline
* Use a Quay.io proxy pull-through cache as an alternative mirroring approach

== Overview

The disconnected install follows a two-phase workflow that separates the _connected_ side
(internet access, pulling images) from the _disconnected_ side (air-gapped cluster, pushing to a
local registry):

[source]
----
Connected ("lowside")                    Air gap                Disconnected ("highside")
 ┌──────────────────────┐                  ║                  ┌──────────────────────────┐
 │ 1. Install oc-mirror │                  ║                  │ 4. Deploy Quay registry  │
 │ 2. Pull secret       │                  ║                  │ 5. Push tar → Quay       │
 │ 3. oc-mirror → tar   │ ── discomedia ──>║──── transfer ──> │ 6. CatalogSource + IDMS  │
 └──────────────────────┘                  ║                  │ 7. Install RHOAI offline │
                                           ║                  └──────────────────────────┘
----

In this lab both sides run on the same cluster for convenience — a pod with a large PVC simulates
the connected mirror host, and the in-cluster Quay registry simulates the private disconnected
registry.

== Exercise 1: Prepare the mirror host (lowside)

Set up a simulated connected host: create a pod with storage, install the oc-mirror v2 CLI, and
provide it registry credentials.

NOTE: The `redhat-operator-index` catalog tag in the imageset configuration
must match your cluster's OpenShift minor (e.g., a 4.22.x cluster needs `v4.22`). This lab is
pinned to `v4.22`. If your cluster differs, update the `catalog:` tag before running oc-mirror.

. Confirm the cluster's OpenShift minor so you can verify it matches the catalog tag:
+
[source,bash,role="execute"]
----
oc get clusterversion version -o jsonpath='{.status.desired.version}{"\n"}'
----

. Create a PVC and pod to simulate the connected mirror host. The PVC needs enough space for
  the mirror workspace (~315 GB for {rhoai-short} operators + dependencies) plus the tar archive:
+
[source,bash,role="execute",subs="attributes"]
----
oc apply -k manifests/02-disconnected/mirror-host
----

. Because the pod cannot reach the OAuth server directly, use a token obtained from outside the `image-download` pod:
+
[source,bash,role="execute",subs="attributes+"]
----
TOKEN=$(oc whoami -t)
echo $TOKEN
----

. Wait for the pod to start, then open a shell inside it:
+
[source,bash,role="execute"]
----
oc rollout status deploy/image-download -n rhoai-deploy --timeout=120s
oc rsh -n rhoai-deploy deploy/image-download
----

. Set the working directory and install oc-mirror v2:
+
[source,bash,role="execute"]
----
export HOME=/mnt && cd /mnt
export PATH=$HOME/.local/bin/:$PATH
----
+
[source,bash,role="execute"]
----
mkdir -p $HOME/.local/bin
curl -L -O https://mirror.openshift.com/pub/cgw/oc-mirror/latest/oc-mirror-rhel9-linux-amd64.tar.gz
tar xzvf oc-mirror-rhel9-linux-amd64.tar.gz
mv oc-mirror $HOME/.local/bin/
----
+
[source,bash,role="execute"]
----
oc-mirror --v2 --help | head -n 1
----

. Log in to the cluster from inside the pod.
+
[source,bash,role="execute",subs="attributes+"]
----
# Back INSIDE the pod — paste the token:
mkdir -p $HOME/.kube
oc login --token=<paste-token-here> \
  --server={openshift_api_server_url} \
  --insecure-skip-tls-verify=true
----

. Provide registry credentials. oc-mirror reads `$HOME/.docker/config.json`; seed it from the
  cluster's own pull secret so pulls from `registry.redhat.io` are authenticated:
+
[source,bash,role="execute"]
----
mkdir -v $HOME/.docker
oc get secret pull-secret -n openshift-config \
  --template='{{index .data ".dockerconfigjson" | base64decode}}' > $HOME/.docker/config.json
----

. Clone the workshop manifests repository:
+
[source,bash,role="execute",subs="attributes"]
----
git clone {repo-url} /mnt/rhoai-deploy-configure
cd /mnt/rhoai-deploy-configure
ls manifests
----

=== Verify

* `oc-mirror --v2 --help` runs without error
* `$HOME/.docker/config.json` exists and contains a `registry.redhat.io` entry
* The cluster minor from `oc get clusterversion` matches the operator `catalog:` tag (`v4.x`)
  in the imageset configuration

== Exercise 2: Mirror images to disk (lowside)

Pull the {rhoai-short} operator catalog and all dependent images into a local tar archive.

. Review the imageset configuration ({rhoai-short} operator + dependencies):
+
ifeval::["{rhoai_version}" == "3.4"]
[source,bash,role="execute"]
----
cat manifests/02-disconnected/imageset-config.yaml
----
endif::[]
ifeval::["{rhoai_version}" == "3.5"]
[source,bash,role="execute"]
----
cat manifests/02-disconnected/imageset-config-35.yaml
----
endif::[]
+
The configuration mirrors eight operators (rhods-operator, rhcl-operator, cert-manager,
leader-worker-set, job-set, cluster-observability-operator, opentelemetry-product, and
custom-metrics-autoscaler) plus three runtime images (vLLM CPU, the modelcar, and PostgreSQL).

. Run the mirror-to-disk phase. This pulls all images and packs them into a tar archive:
+
ifeval::["{rhoai_version}" == "3.4"]
[source,bash,role="execute"]
----
export HOME=/mnt && cd /mnt/rhoai-deploy-configure
export PATH=$HOME/.local/bin/:$PATH

oc-mirror --config manifests/02-disconnected/imageset-config.yaml \
  file:///mnt/oc-mirror-workspace --v2
----
endif::[]
ifeval::["{rhoai_version}" == "3.5"]
[source,bash,role="execute"]
----
export HOME=/mnt && cd /mnt/rhoai-deploy-configure
export PATH=$HOME/.local/bin/:$PATH

oc-mirror --config manifests/02-disconnected/imageset-config-35.yaml \
  file:///mnt/oc-mirror-workspace --v2
----
endif::[]
+
This takes approximately 5 minutes to download and 18 minutes to create the tar archive (~23
minutes total). Expected output:
+
[source]
----
196 / 196 (44m53s) [============================] 100 %
✓  193 / 193 operator images mirrored successfully
✓  3 / 3 additional images mirrored successfully
📦 Preparing the tarball archive...
mirror time     : 54m22s
👋 Goodbye, thank you for using oc-mirror
----

. Verify the tar archive was created:
+
[source,bash,role="execute"]
----
ls -lh /mnt/oc-mirror-workspace/mirror_000001.tar
df -h /mnt
----
+
The archive is approximately 314 GB. The working directory uses additional space during the
build but can be cleaned up after the tar is confirmed:
+
[source,bash,role="execute"]
----
rm -rf /mnt/.oc-mirror
----

=== Verify

* `mirror_000001.tar` exists in `/mnt/oc-mirror-workspace/` (~314 GB)
* oc-mirror reported all images mirrored successfully with no errors

TIP: In a real air-gap scenario, you would now transfer the tar archive (and the imageset
configuration YAML) to a portable medium and carry it across the air gap to the disconnected side.

== Exercise 3: Deploy Quay mirror registry (highside)

On the disconnected side, deploy a Quay registry to receive the mirrored images. In this lab
the Quay operator was already installed via the `bootstrap-infra` Helm chart; you initialize the
admin user and create a mirror organization.

NOTE: In a production disconnected environment you would typically use a dedicated mirror registry
(the `mirror-registry` tool, a standalone Quay appliance, or an existing enterprise registry).
This lab uses the in-cluster Quay for convenience.

. Get the Quay registry endpoint:
+
[source,bash,role="execute"]
----
export QUAY_URL=$(oc get quayregistry registry -n quay -o jsonpath='{.status.registryEndpoint}')
echo $QUAY_URL
----

. Initialize the Quay admin user (only works on first run when `FEATURE_USER_INITIALIZE` is
  enabled):
+
[source,bash,role="execute"]
----
curl -sSk -X POST "${QUAY_URL}/api/v1/user/initialize" \
  -H "Content-Type: application/json" \
  -d '{"username":"quayadmin","password":"quayadmin","email":"quayadmin@example.com","access_token":true}'
----
+
Save the `access_token` from the response — you need it for the next step.

. Create a `mirror` organization to hold the mirrored images:
+
[source,bash,role="execute"]
----
TOKEN="<access_token from previous step>"

curl -sSk -X POST "${QUAY_URL}/api/v1/organization/" \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{"name":"mirror","email":"mirror@example.com"}'
----

=== Verify

* The Quay route is accessible: `curl -sSk ${QUAY_URL}/health/instance | jq .status_code`
  returns `200`
* The `mirror` organization exists in the Quay UI

== Exercise 4: Push the tar archive to Quay (highside)

Push the disk archive into the Quay mirror registry using oc-mirror's diskToMirror workflow.

. The mirror pod needs to reach the Quay registry by hostname. On this cluster the internal
  router serves `*.apps` routes — patch the deployment with a `hostAliases` entry so the pod
  resolves the Quay hostname to the internal router:
+
[source,bash,role="execute"]
----
ROUTER_IP=$(oc get svc router-internal-default -n openshift-ingress -o jsonpath='{.spec.clusterIP}')
CLUSTER_DOMAIN=$(oc get ingresses.config.openshift.io cluster -o jsonpath='{.spec.domain}')
QUAY_HOST="registry-quay-quay.${CLUSTER_DOMAIN}"
----
+
[source,bash,role="execute"]
----
oc patch deploy image-download -n rhoai-deploy --type=json \
  -p "[{\"op\":\"add\",\"path\":\"/spec/template/spec/hostAliases\",\"value\":[{\"ip\":\"${ROUTER_IP}\",\"hostnames\":[\"${QUAY_HOST}\"]}]}]"

oc rollout status deploy/image-download -n rhoai-deploy --timeout=120s
----
+
NOTE: This step is specific to this lab environment where the pod network cannot route to the
cluster's external ingress VIP. In a production disconnected environment the mirror host would
resolve the registry hostname normally.

. Open a shell in the new pod:
+
[source,bash,role="execute"]
----
oc rsh -n rhoai-deploy deploy/image-download
----

. Verify DNS resolution and log in to Quay:
+
[source,bash,role="execute"]
----
export HOME=/mnt
export PATH=$HOME/.local/bin/:$PATH
export XDG_RUNTIME_DIR=/mnt/.runtime
mkdir -p ${XDG_RUNTIME_DIR}/containers
CLUSTER_DOMAIN=$(oc get ingresses.config.openshift.io cluster -o jsonpath='{.spec.domain}')
QUAY_HOST="registry-quay-quay.${CLUSTER_DOMAIN}"

# Verify the hostname resolves to the internal router
grep ${QUAY_HOST} /etc/hosts

# Login to Quay
skopeo login --tls-verify=false -u quayadmin -p quayadmin ${QUAY_HOST}
----

. Run the diskToMirror phase — pushes all images from the tar archive into Quay (logs to /mnt/oc-mirror-push.log):
+
ifeval::["{rhoai_version}" == "3.4"]
[source,bash,role="execute"]
----
cd /mnt/rhoai-deploy-configure

oc-mirror -c manifests/02-disconnected/imageset-config.yaml \
  --from file:///mnt/oc-mirror-workspace \
  docker://${QUAY_HOST}/mirror \
  --dest-tls-verify=false \
  --log-level debug \
  --v2
----
endif::[]
ifeval::["{rhoai_version}" == "3.5"]
[source,bash,role="execute"]
----
cd /mnt/rhoai-deploy-configure

oc-mirror -c manifests/02-disconnected/imageset-config-35.yaml \
  --from file:///mnt/oc-mirror-workspace \
  docker://${QUAY_HOST}/mirror \
  --dest-tls-verify=false \
  --v2
----
endif::[]
+
This is a long upload — expect it to take ~60+ minutes depending on storage and network
throughput.
+
At this point you can leave the pod running and continue with the next Module - the remaining steps are reference only in this lab as our cluster is already installed with RHOAI via the connected path.
+
image::34-quay-repos.png[Quay Repositories,link=self,window=blank,width=800]
* The Quay UI shows repositories under the `mirror` organization

=== Verify

* oc-mirror reports all images pushed successfully
* The Quay UI shows repositories under the `mirror` organization
* oc-mirror generates cluster resources under
  `oc-mirror-workspace/working-dir/cluster-resources/`

== Exercise 5: Install the local CatalogSource

[IMPORTANT]
====
oc-mirror generates `ImageDigestMirrorSet`, `ImageTagMirrorSet`, and `CatalogSource` manifests
in the `cluster-resources/` directory. In this lab *do not apply them* — the Quay registry is
hosted on the same cluster, so redirecting image pulls to it creates a circular dependency (if
Quay goes down, the cluster cannot pull images to recover it). In a production disconnected
environment the mirror registry runs on separate infrastructure and these manifests would be
applied to configure the cluster.
====

oc-mirror generates two resource types that configure the cluster to pull from your mirror registry
instead of the internet. In a production disconnected environment you would apply both; in this lab
reference copies are provided under `manifests/02-disconnected/catalog/`.

The **`CatalogSource`** tells OLM where to find the operator index image — your mirror registry
instead of `registry.redhat.io`:

[source,yaml]
----
apiVersion: operators.coreos.com/v1alpha1
kind: CatalogSource
metadata:
  name: cs-redhat-operator-index              # <1>
  namespace: openshift-marketplace
spec:
  sourceType: grpc
  image: REGISTRY_URL/redhat/redhat-operator-index:v4.22  # <2>
  displayName: Mirrored Red Hat Operators
  publisher: Red Hat
  updateStrategy:
    registryPoll:
      interval: 10m                            # <3>
----
<1> oc-mirror names this `cs-redhat-operator-index` — it replaces (or supplements) the
    default `redhat-operators` catalog.
<2> Replace `REGISTRY_URL` with your mirror registry hostname. oc-mirror's generated version
    uses the exact digest it pushed.
<3> The catalog pod re-polls the registry image every 10 minutes for updated operator bundles.

The **`ImageDigestMirrorSet`** (IDMS) redirects image pulls cluster-wide — any pod requesting
an image from `registry.redhat.io` or `quay.io` transparently pulls from your mirror instead:

[source,yaml]
----
apiVersion: config.openshift.io/v1
kind: ImageDigestMirrorSet
metadata:
  name: rhoai-disconnected
spec:
  imageDigestMirrors:
    - source: registry.redhat.io              # <1>
      mirrors:
        - REGISTRY_URL                        # <2>
    - source: quay.io
      mirrors:
        - REGISTRY_URL
----
<1> Every image pull that would normally go to `registry.redhat.io` is redirected.
<2> The mirror registry URL. oc-mirror's generated version includes the full namespace path
    (e.g., `registry-quay-quay.apps.cluster.example.com/mirror`).

NOTE: oc-mirror may also generate an `ImageTagMirrorSet` (ITMS) for tag-referenced images.
The IDMS handles digest-referenced images; the ITMS handles tag-referenced ones. Apply both
if generated.

WARNING: *Do not run these commands in this lab.* The Quay mirror registry is hosted on the same
cluster. Applying the IDMS would redirect all image pulls to Quay — if Quay restarts, the cluster
cannot pull images to recover it (chicken-and-egg). In a production disconnected environment the
mirror registry runs on separate infrastructure and these steps would be safe to execute.

. Apply the pre-built CatalogSource and mirror resources:
+
[source,bash]
----
oc apply -k manifests/02-disconnected/catalog
----

. Confirm the catalog source becomes `READY`:
+
[source,bash]
----
oc get catalogsource -n openshift-marketplace
----

=== Verify

* The {rhoai-short} operator is installable from the local catalog (visible in OperatorHub), with no
  external image pulls:
+
[source,bash]
----
oc get packagemanifest | grep rhods-operator
----

With the catalog serving images locally, the install steps are identical to the connected path.

== Exercise 6: Complete the DataScienceCluster offline

IMPORTANT: *Do not run these commands in this lab* — RHOAI is already installed via the connected
path (Module 1). This exercise documents what the disconnected install would look like on a
production air-gapped cluster with a separate mirror registry.

. Install the operator from the local catalog and create the DSC:
+
[source,bash]
----
oc apply -k manifests/01-install/operator

  --for=jsonpath='{.status.phase}'=Succeeded --timeout=15m
oc apply -k manifests/01-install/dsc
oc wait datasciencecluster/default-dsc --for=condition=Ready --timeout=20m
----

=== Verify

* The DSC reports a `Ready` phase with no external pulls:
+
[source,bash]
----
oc get datasciencecluster default-dsc -o jsonpath='{.status.phase}{"\n"}'
----

NOTE: If you completed Exercises 1–6 on a production disconnected cluster, you have reached the
same "RHOAI Ready" state as Module 1. Exercise 7 describes a lighter-weight alternative for lab
environments — skip it if the full oc-mirror path is what your production environment requires.

== Exercise 7 (Alternative): Quay.io proxy pull-through cache

For lab environments, a Quay.io transparent proxy pull-through cache avoids a full oc-mirror run.

. Enable proxy caching on your Quay instance by setting `FEATURE_PROXY_CACHE: true` in the Quay
  config, then create the cache organization pointing upstream at `registry.redhat.io`.

. Point the cluster at the cache with an `ImageDigestMirrorSet`:
+
[source,bash,role="execute"]
----
oc apply -f manifests/02-disconnected/proxy-cache-idms.yaml
----

=== Verify

* Pulling a RHOAI image resolves through the cache namespace on your Quay host (the first pull
  populates the cache; subsequent pulls are served locally).

== Module summary

**What you accomplished:**

* Set up a simulated connected mirror host with oc-mirror v2
* Mirrored {rhoai-short} operator images into a tar archive using the two-phase disk workflow
* Deployed a Quay mirror registry and pushed the archive into it
* Applied a local `CatalogSource` and `ImageDigestMirrorSet` so the cluster resolves images from the private registry
* Completed the `DataScienceCluster` install offline, reaching the same "RHOAI Ready" state as Module 1

**Key takeaways:**

* The `redhat-operator-index` catalog tag must match your cluster's OpenShift minor — a mismatch causes operator dependency failures
* oc-mirror v2 separates image collection (Phase 1, connected) from cluster-side population (Phase 2, disconnected), enabling true air-gapped workflows
* The imageset configuration pins operator channels to match the Subscription channels used by the workshop manifests — mismatches cause oc-mirror to abort with "a new default channel must be configured"
* A Quay proxy pull-through cache is a lower-friction alternative for lab or dev environments where a full oc-mirror workflow is too heavyweight

Continue to xref:module-03-model-serving-platform.adoc[Module 3] to prepare the model-serving platform — the path is the same whether you followed the connected or disconnected install.
