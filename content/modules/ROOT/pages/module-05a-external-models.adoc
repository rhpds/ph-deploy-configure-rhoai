= Module 5a: External Models with MaaS
:navtitle: Module 5a: External Models
:toc: macro
:toclevels: 1
:icons: font

The `ExternalModel` CRD lets you expose third-party LLM APIs — or any OpenAI-compatible endpoint —
through the MaaS gateway. External models get the same API key management, subscription rate
limits, authentication, and telemetry as locally-served models.

In this module you deploy *llm-katan*, a lightweight simulator that mimics OpenAI, Anthropic,
Azure OpenAI, Bedrock, and Vertex AI in echo mode. It runs entirely in-cluster — no real API keys
or external internet access needed — making it an ideal vehicle for learning the {maas} external
model workflow.

[IMPORTANT]
====
*Technology Preview.* External model support is a Technology Preview feature in {rhoai}
{rhoai_version}. APIs and behaviour may change.
====

== Prerequisites

* xref:module-05-maas-governance.adoc[Module 5] complete (MaaS gateway running, at least one subscription
  exists)
* `helm` v3 installed on the bastion / workshop host
* The workshop git repository cloned and the shell at its root

== Learning objectives

* Understand the {rhoai-short} {rhoai_version} external model resource model
* Deploy and verify the llm-katan simulator (echo-mode, no GPU)
* Publish simulator models through the MaaS gateway and call them with an API key
* Observe all five provider types in *Gen AI studio -> AI asset endpoints*

== Resource model (RHOAI 3.5+)

An external model in {rhoai-short} {rhoai_version} requires six resources:

[cols="1,3",options="header"]
|===
|Resource |Purpose

|`Secret`
|Stores the provider API key. Must have the label `inference.llm-d.ai/ipp-managed: "true"` so the
 Inference Payload Processor (IPP) injects it into upstream requests.

|`ExternalProvider`
|Defines the provider endpoint URL, auth type, and a reference to the credential Secret.

|`ExternalModel`
|Maps the client-facing model name to the provider with routing config (`apiFormat`, `path`,
 `targetModel`).

|`MaaSModelRef`
|Registers the `ExternalModel` in the MaaS catalog so it appears in `/maas-api/v1/models`.

|`MaaSAuthPolicy`
|Grants access to specific users or groups.

|`MaaSSubscription`
|Sets token rate limits and subscription priority.
|===

NOTE: IPP (Inference Payload Processor) is deployed automatically into `openshift-ingress` by
{rhoai-short} {rhoai_version}. It translates OpenAI chat format to each provider's native wire format
before forwarding to the upstream endpoint.

[NOTE]
.Two ways to author an external model
====
There are two CRD layers you can author against:

* *High-level* `maas.opendatahub.io/ExternalModel` — a compact CR (`provider`, `endpoint`,
  `targetModel`, `credentialRef`). The MaaS controller expands it into the low-level
  `inference.opendatahub.io` `ExternalProvider` + `ExternalModel`, HTTPRoutes, Services and
  routing. This is what four of the five simulator providers use.
* *Low-level* `inference.opendatahub.io` `ExternalProvider` + `ExternalModel` — authored directly.
  The `ExternalProvider` has a first-class `config` object for provider-specific settings, and the
  `ExternalModel` carries the request `path`, `apiFormat`, and `targetModel` per provider ref.

*Vertex AI needs the low-level form.* Its request path is a template —
`/v1/projects/{project}/locations/{location}/endpoints/{endpoint}/chat/completions` — whose
placeholders resolve from the provider `config`. The high-level `ExternalModel` CRD has no `config`
field, so the placeholders would stay unresolved and the model would fail to reconcile. The chart
detects a `config:` block on a provider and emits the low-level pair for it instead
(`manifests/05-maas/llm-katan-simulator/templates/external-models.yaml`). `MaaSModelRef` resolves
by `kind: ExternalModel` either way, so governance (subscription, auth policy, rate limits) is
identical for both layers.
====

== Exercise 1: Deploy the llm-katan simulator

The llm-katan Helm chart deploys a simulator pod and creates `ExternalProvider` + `ExternalModel`
CRs for each of the five supported provider types. The ExternalModel controller then creates the
HTTPRoutes and Services that wire them to `maas-default-gateway`.

Every `ExternalModel` references a credential `Secret`. The secret must carry the label
`inference.llm-d.ai/ipp-managed: "true"` so the Inference Payload Processor (IPP) injects the
API key into upstream requests. Because llm-katan is an echo simulator it does not validate API
keys — a dummy value is sufficient:

Inspect the chart template:

[source,bash,role="execute"]
----
cat manifests/05-maas/llm-katan-simulator/templates/secrets.yaml
----

[source,yaml]
----
apiVersion: v1
kind: Secret
metadata:
  name: sim-openai                           # <1>
  namespace: llm-katan
  labels:
    inference.llm-d.ai/ipp-managed: "true"   # <2>
type: Opaque
stringData:
  api-key: "sim-fake-key"                    # <3>
----
<1> Name must match the `credentialRef.name` in the `ExternalModel`.
<2> Required label — IPP watches for secrets with this label and injects the `api-key`
    value as the `Authorization: Bearer` header on upstream requests.
<3> Any non-empty value works for llm-katan. For a real provider this would be the actual
    API key (OpenAI, Anthropic, Azure, etc.).

The chart renders two kinds of external model. Four providers use the **high-level** maas
`ExternalModel` — here is `sim-openai` as an example:

Inspect the chart template:

[source,bash,role="execute"]
----
cat manifests/05-maas/llm-katan-simulator/templates/external-models.yaml
----

[source,yaml]
----
apiVersion: maas.opendatahub.io/v1alpha1
kind: ExternalModel                    # <1>
metadata:
  name: sim-openai
  namespace: llm-katan
  annotations:
    maas.opendatahub.io/tls: "false"
spec:
  provider: openai                     # <2>
  targetModel: sim-openai              # <3>
  endpoint: sim.llm-katan.svc.cluster.local  # <4>
  credentialRef:
    name: sim-openai                   # <5>
----
<1> High-level `maas.opendatahub.io` ExternalModel — the MaaS controller expands this into
    the low-level `inference.opendatahub.io` ExternalProvider + ExternalModel, HTTPRoutes,
    Services, and DestinationRules automatically.
<2> Provider wire format — IPP translates the request to this provider's native API.
<3> The model name the upstream (simulator) serves.
<4> In-cluster simulator service. The MaaS controller creates an ExternalName Service that
    routes through the Istio mesh with TLS origination.
<5> Secret containing the API key (labelled `inference.llm-d.ai/ipp-managed: "true"` so IPP
    injects it into upstream requests).

Each `ExternalModel` is published through a **`MaaSModelRef`** — the same pattern as locally-served
models in Module 5:

Inspect the chart template:

[source,bash,role="execute"]
----
cat manifests/05-maas/llm-katan-simulator/templates/maasmodelrefs.yaml
----

[source,yaml]
----
apiVersion: maas.opendatahub.io/v1alpha1
kind: MaaSModelRef
metadata:
  name: sim-openai
  namespace: llm-katan                 # <1>
spec:
  modelRef:
    kind: ExternalModel                # <2>
    name: sim-openai
----
<1> Must be in the same namespace as the `ExternalModel`.
<2> `kind: ExternalModel` — resolves to either the high-level maas or low-level inference
    variant. Governance (subscription, auth policy, rate limits) works identically for both.

Vertex AI uses the **low-level** `inference.opendatahub.io` ExternalProvider + ExternalModel
directly (see the NOTE in the resource model section above for why). The same chart template
handles both high-level and low-level forms — providers with a `config:` block in `values.yaml`
emit the low-level pair:

[source,yaml]
----
apiVersion: inference.opendatahub.io/v1alpha1
kind: ExternalProvider                 # <1>
metadata:
  name: sim-vertex-openai
  namespace: llm-katan
spec:
  provider: vertex-openai
  endpoint: sim.simulator              # <2>
  auth:
    type: apikey
    secretRef:
      name: sim-vertex-openai
  config:                              # <3>
    project: sim-project
    location: us-central1
    endpoint: sim-endpoint
---
apiVersion: inference.opendatahub.io/v1alpha1
kind: ExternalModel                    # <4>
metadata:
  name: sim-vertex-openai
  namespace: llm-katan
spec:
  modelName: sim-vertex-openai
  externalProviderRefs:
    - ref:
        name: sim-vertex-openai
      targetModel: sim-vertex-openai
      apiFormat: openai-chat
      path: /v1/projects/{project}/locations/{location}/endpoints/{endpoint}/chat/completions  # <5>
      weight: 1
----
<1> Low-level ExternalProvider — a first-class `config` object for provider-specific settings.
<2> `sim.simulator` — the mesh-internal host with the skip-verify DestinationRule (see the
    two-layer NOTE above). The EP controller owns the generated Service and sets its
    `externalName` to this value.
<3> Project, location, and endpoint values that resolve the `{placeholder}` tokens in the
    request path. These are dummy values for the simulator.
<4> Low-level ExternalModel — carries the request path, API format, and provider ref.
<5> The path template — placeholders resolve from the ExternalProvider's `config` at
    reconcile time.

. Deploy the simulator with `helm template` piped into `oc apply --server-side`. The
  `--server-side` flag is required because the ExternalModel controller creates resources from the
  ExternalModel CRs (HTTPRoutes, Services) that would otherwise conflict with `helm install`
  field ownership:
+
[source,bash,role="execute"]
----
helm template sim manifests/05-maas/llm-katan-simulator --skip-crds \
  | oc apply --server-side --force-conflicts -f -
----

. The `ipp-legacy-migration` controller migrates each high-level maas `ExternalModel` into a
  low-level inference `ExternalProvider` with `endpoint` set to the raw cluster service
  (`sim.llm-katan.svc.cluster.local`). That host has no `insecureSkipVerify` DestinationRule,
  so the simulator's self-signed TLS cert is rejected. Patch the migrated ExternalProviders to
  use `sim.simulator` — the mesh-internal host that carries the skip-verify DR:
+
[source,bash,role="execute"]
----
for model in openai anthropic azure-openai bedrock; do
  oc patch externalproviders.inference.opendatahub.io sim-${model} -n llm-katan \
    --type=merge -p '{"spec":{"endpoint":"sim.simulator"}}'
done
----
+
[NOTE]
====
This step is not needed for `sim-vertex-openai` — it is authored directly as a low-level
`ExternalProvider` with `endpoint: sim.simulator` in the chart, so it already uses the
working TLS path. This is a platform bug fixed by
`models-as-a-service` PR #1417 (see *Known caveats* below). Once that fix ships, the
migrated ExternalProviders will inherit the correct endpoint and this patch becomes
unnecessary.
====

. Wait for the simulator to start. First boot installs llm-katan from PyPI (~60 s):
+
[source,bash,role="execute"]
----
oc rollout status deployment/sim -n llm-katan --timeout=180s
oc logs -n llm-katan deploy/sim --tail=5
----
+
Expected last log line: `LLM Katan ready on 0.0.0.0:8443`

== Exercise 2: Mint an API key and call each provider

. Create a key scoped to the simulator subscription:
+
[source,bash,role="execute"]
----
export CLUSTER_DOMAIN=$(oc get ingresses.config.openshift.io cluster -o jsonpath='{.spec.domain}')
export HOST="https://maas.${CLUSTER_DOMAIN}"
export SIM_KEY=$(curl -sSk -X POST "${HOST}/maas-api/v1/api-keys" \
  -H "Authorization: Bearer $(oc whoami -t)" \
  -H "Content-Type: application/json" \
  -d '{"name":"sim-key","expiresIn":"1h","subscription":"sim-models-subscription"}' | jq -r .key)
echo "Simulator key: ${SIM_KEY:0:12}..."
----

. Call each provider. The MaaS gateway supports two routing modes:
+
--
*Body-based routing (recommended).* Send all requests to `${HOST}/v1/chat/completions` and
specify the model in the JSON body — the same OpenAI-compatible pattern that SDKs and
application frameworks use. The gateway reads the `model` field from the request body
and routes to the correct backend:

[source,bash,role="execute"]
----
for model in sim-openai sim-anthropic sim-azure-openai sim-bedrock sim-vertex-openai; do
  echo "--- ${model} ---"
  curl -sSk "${HOST}/v1/chat/completions" \
    -H "Authorization: Bearer ${SIM_KEY}" \
    -H "Content-Type: application/json" \
    -d "{\"model\":\"${model}\",\"messages\":[{\"role\":\"user\",\"content\":\"Hello\"}]}" \
    | jq -Rr '(fromjson? | .choices[0].message.content // .content[0].text) // .'
done
----

image::23-maas-llm-katan-simluator.png[MaaS LLM Katan Simulator Models,link=self,window=blank,width=800]

*Path-based routing.* Encode the model in the URL path as
`${HOST}/<namespace>/<model>/v1/chat/completions`. This is useful for debugging (each model
has a distinct URL) but couples the client to the cluster's namespace layout:

[source,bash,role="execute"]
----
for model in sim-openai sim-anthropic sim-azure-openai sim-bedrock sim-vertex-openai; do
  echo "--- ${model} ---"
  curl -sSk "${HOST}/llm-katan/${model}/v1/chat/completions" \
    -H "Authorization: Bearer ${SIM_KEY}" \
    -H "Content-Type: application/json" \
    -d "{\"model\":\"${model}\",\"messages\":[{\"role\":\"user\",\"content\":\"Hello\"}]}" \
    | jq -Rr '(fromjson? | .choices[0].message.content // .content[0].text) // .'
done
----
--
+
[NOTE]
====
Each provider echoes back in its own API's native response schema. OpenAI-format
providers (`sim-openai`, `sim-azure-openai`, `sim-bedrock`) return the text under
`.choices[0].message.content`, while `sim-anthropic` uses the Anthropic Messages
shape (`.content[0].text`). The `jq` filter above handles both, and reads the body
raw first (`fromjson?`) so a non-JSON error body prints as text instead of failing
the loop.
====

== Exercise 3: View simulator metrics in the Observability dashboard

The llm-katan simulator exposes native Prometheus metrics at `/metrics` on the same
port as its API. The chart deploys a `ServiceMonitor` labelled
`monitoring.opendatahub.io/scrape: "true"`, which is picked up by the RHOAI
OpenTelemetry data-science collector Target Allocator. Metrics flow:

[source]
----
llm-katan pod /metrics  →  OTel collector (data-science)
  →  data-science Prometheus  →  data-science-prometheus-datasource (Perses)
----

. Apply the External Models dashboard manifest (deployed alongside the chart but
  in a different namespace):
+
[source,bash,role="execute"]
----
oc apply -f manifests/05-maas/perses-dashboard-external-models.yaml
----

. In the {rhoai-short} dashboard go to *Observe & monitor → Dashboard*.
  A new *External Models* tab appears alongside Cluster, Models, LLM Traffic, etc.

. Fire the Exercise 2 curl loop to generate some traffic, then refresh the
  dashboard. You should see:
** *Lifetime requests* — total requests since the simulator started (persisted across pod restarts)
** *Requests/s by provider* — per-provider breakdown (`openai`, `anthropic`, `azure_openai`, `vertexai (openai-compat)`, `bedrock`)
** *Token throughput* — prompt and completion token rates
** *Avg response time* — rolling average over the last 1000 requests

[NOTE]
====
The token counters in this dashboard reset on pod restart. For durable token accounting
(which survives restarts and tracks by API key) use the *Usage* tab, which draws from
the MaaS gateway's Limitador subscription counters.
====

[NOTE]
.Why only four provider series?
====
The `provider` label in the simulator's metrics reflects the wire format the sim actually
receives, not the MaaS provider type declared in the `ExternalModel`. The four high-level
providers (OpenAI, Anthropic, Azure OpenAI, Bedrock) all reach the sim via the MaaS
gateway in their respective wire formats — but Bedrock calls arrive at the sim's
`/v1/chat/completions` endpoint in OpenAI format (the gateway abstracts the format), so
the sim classifies them as `openai`. Only `sim-vertex-openai` gets its own label
(`vertexai (openai-compat)`) because it is authored as a low-level inference
`ExternalProvider` with a distinct URL path that the sim recognises as its Vertex AI
handler. In practice this means the `openai` series represents both `sim-openai` and
`sim-bedrock` traffic combined.
====

=== Known caveats

[NOTE]
.Intermittent HTTP 500 on a loaded cluster
====
On a heavily loaded single-node cluster you may see an occasional `500` (or a non-JSON
error body) from an otherwise-healthy provider. This is a known upstream Envoy
race in the WASM remote-code fetch used by the gateway
(link:https://github.com/envoyproxy/envoy/pull/46674[envoyproxy/envoy#46674]) — the
gateway log shows `Wasm remote code fetch is unstable and may cause a crash`. It is
*not* a simulator or configuration problem. Re-run the call; it succeeds on retry. The
verify loop above reads the body raw first so a transient error prints as text rather
than aborting the loop.
====

[NOTE]
.External models appear in Usage only — not in LLM Traffic / LLM Performance / Models
====
In the Observability dashboard (*Observe & monitor → Dashboard*), the sim models appear
under the *Usage* tab (MaaS subscription token counters, tracked at the gateway layer) but
are absent from the *LLM Traffic*, *LLM Performance*, and *Models* tabs. Those tabs query
KServe and vLLM pod metrics (`kserve_vllm:*`, `inference_model_request_*`) which only exist
for locally-served `LLMInferenceService` workloads with a vLLM sidecar. The sim models are
an external echo server with no vLLM — so no pod metrics are scraped. This is expected
behaviour: *Usage* is the right place to observe external model consumption.
====

[NOTE]
.Duplicate HTTPRoutes for the high-level providers (known platform issue)
====
On this {rhoai-short} {rhoai_version} build, `oc get httproute -n llm-katan` shows two
routes per high-level provider — `maas-sim-<name>` and `sim-<name>` — both matching
`/llm-katan/sim-<name>` on the same gateway. On a 3.4->3.5 migration the maas
`ExternalModel` controller still creates its own legacy `maas-*` routing while the IPP
controller *also* creates routing from the migrated inference `ExternalModel`. The
`maas-*` copy routes to the raw service host (no skip-verify DestinationRule), so it is
the non-working TLS path; the gateway deterministically resolves the path conflict to
the working `sim-<name>` route, so calls still succeed.

This is fixed upstream in `models-as-a-service` (link:https://github.com/opendatahub-io/models-as-a-service/pull/1417[PR #1417]),
which tears down the `maas-*` children once the migrated inference route is ready. 
Until that fix ships in your build, the duplicate is cosmetic clutter.
The low-level provider (`sim-vertex-openai`) is authored directly
against the inference CRDs, bypasses the legacy reconciler entirely, and already
produces a single route.
====

== Exercise 1: Deploy the llm-katan simulator

static manifests in `manifests/05-maas/external-model-34/` deploy the simulator Deployment/Service

metadata:
  name: sim-openai-key                                  # <1>
  namespace: llm-katan
  labels:
    inference.networking.k8s.io/bbr-managed: "true"     # <2>
type: Opaque

  api-key: "sim-fake-key"                               # <3>

<1> Name must match the `credentialRef.name` in the `ExternalModel`.
<2> Required label — the BBR ext-proc watches for secrets with this label and injects the

Inspect the manifest:

[source,bash,role="execute"]

<1> The upstream API format — MaaS translates wire format accordingly.
<2> The model name the simulator serves (llm-katan's `--served-model-name`).
<3> In-cluster endpoint of the simulator pod — direct Service DNS, port 8443 (TLS).
<4> References the `Secret` created in the previous step. The BBR label on the secret
    tells the ext-proc to inject the API key into upstream requests.

== Exercise 2: Mint an API key and call the simulator

. Create a key scoped to the simulator subscription:
+
[source,bash,role="execute"]
----
export CLUSTER_DOMAIN=$(oc get ingresses.config.openshift.io cluster -o jsonpath='{.spec.domain}')
export HOST="https://maas.${CLUSTER_DOMAIN}"
export SIM_KEY=$(curl -sSk -X POST "${HOST}/maas-api/v1/api-keys" \
  -H "Authorization: Bearer $(oc whoami -t)" \
  -H "Content-Type: application/json" \
  -d '{"name":"sim-key","expiresIn":"1h","subscription":"sim-models-subscription"}' | jq -r .key)
echo "Simulator key: ${SIM_KEY:0:12}..."
----

. Call the simulator endpoint:
+
[source,bash,role="execute"]
----
curl -sSk "${HOST}/llm-katan/sim-openai/v1/chat/completions" \
  -H "Authorization: Bearer ${SIM_KEY}" \
  -H "Content-Type: application/json" \
  -d '{"model":"sim-openai","messages":[{"role":"user","content":"Hello"}]}' \
  | jq -r '.choices[0].message.content'
----

=== Verify

* The call returns HTTP 200 with an echo response containing the input message.
